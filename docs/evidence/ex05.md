## 1. Setting and prediction

This is the simulated case from the ex05 handout. The check that failed is `curl -Iv https://site.lab.example/`, which sends a HEAD request to the domain and prints each step along the way.

If everything were working, I would expect:

- `dig` to resolve the domain to Railway,
- `curl` to connect and the certificate to verify as `site.lab.example`,
- the site to return `200`.

## 2. Failed check and evidence

All output quoted here is simulated and was supplied by the handout, not run by me. I reviewed it on October 11, 2026. The two supplied commands are:

1. `dig site.lab.example A +noall +answer`, to see where the domain points.
2. `curl -Iv https://site.lab.example/`, to request the page.

The output:

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

- **DNS:** the domain still points to `198.51.100.24`, which the handout identifies as the old Azure server, and not to Railway.
- **Connection:** curl connected successfully to that server.
- **Certificate:** the server presented a certificate for `old-vm.lab.example`. That name doesn't match `site.lab.example`, so curl stopped with error 60.

## 3. Diagnosis

**DNS comes first.** The zone still holds the record `site.lab.example.  300  IN  A  198.51.100.24`, so `dig` returns the old VM's address instead of Railway's. The output only shows the record as it is now, not its history, but the most likely explanation is that it wasn't updated during the migration.

**TLS fails as a result.** Because DNS sends curl to the old VM, the VM presents its own certificate for `old-vm.lab.example`. The name doesn't match `site.lab.example`, so validation fails with curl error 60 before any response is sent.

**One root cause.** The stale DNS record is the real problem. The certificate mismatch is a consequence of it, not a separate fault.

**Where the record lives.** Cloudflare is authoritative for `lab.example`, and the record is DNS only (not proxied). So the certificate curl sees comes straight from the server at `198.51.100.24`, not from Cloudflare. The fix belongs in the Cloudflare zone.

**Still uncertain:** the handout says the Railway-provided URL already returns the current page and database content, so the app itself works. What the failed check can't show is whether Railway will serve `site.lab.example` with a valid certificate once DNS points there, because curl never reaches Railway.

## 4. Repair and repeated check

**Fix:** replace the A record `site.lab.example → 198.51.100.24` with a CNAME `site.lab.example → current-app.up.railway.app`, and leave the rest of the configuration unchanged, since the handout states the ownership TXT record has already verified.

**Why DNS and not TLS:** `dig` returned the old `198.51.100.24`, and curl connected to that same address. The certificate error follows from reaching the wrong server, so fixing the certificate alone wouldn't help.

Below is the simulated follow-up supplied by the handout. I interpreted this output; I did not run these commands.

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

The `dig` output shows the A record has been replaced with a CNAME to `current-app.up.railway.app`, which resolves to `203.0.113.44`. Compared with section 2:

| | Before | After |
|---|---|---|
| DNS answer | `A 198.51.100.24` | `CNAME current-app.up.railway.app` → `A 203.0.113.44` |
| Connected address | `198.51.100.24` | `203.0.113.44` |
| Certificate | `old-vm.lab.example` | `site.lab.example` |
| curl result | error 60 | `HTTP/2 200` |

**Compared with my proposal:** the record change in the follow-up is the one I proposed, replacing the A record with a CNAME to `current-app.up.railway.app`. The handout says the operator made only that one record change, so the repeated checks support my initial diagnosis and I don't need to revise it. The DNS fault came first: the certificate mismatch only appeared because DNS sent curl to the old server, and it went away once DNS pointed at Railway.

**Still not proven:** `curl -I` sends a HEAD request, so `HTTP/2 200` shows that the custom domain answers over valid HTTPS, not that the page body and database content come through. The handout says the Railway URL already serves them, so this is likely. In a real cutover, a full `curl https://site.lab.example/` or a browser check would confirm it.

## 5. What you learned

**A test that isolates DNS.** Point curl straight at Railway's IP:

```
curl --resolve site.lab.example:443:203.0.113.44 https://site.lab.example/
```

This skips the DNS lookup and talks directly to the Railway server. If it returns a valid `site.lab.example` certificate and `HTTP/2 200` while the normal curl fails, DNS is the cause. If both fail the same way, the problem is in the TLS layer or the application itself.

**If the error continued after the CNAME change**, I would work through it in order:

1. **DNS:** query a public resolver (`dig @1.1.1.1 site.lab.example`) and check again later, to rule out propagation delay.
2. **Certificate:** if DNS looks right but the certificate is wrong, check that Railway has issued a certificate for the domain.
3. **Application:** if the certificate is right but the page or data is wrong, check the Railway deployment directly. Correct DNS doesn't guarantee anything beyond that.
