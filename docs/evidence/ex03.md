## 2. What went wrong, how I investigated, and what confirmed the fix

### The region and size in the guide weren't available

- **What broke:** the guide's VM (West US 2, `Standard_B2ts_v2`) couldn't be created on my Azure for Students subscription.
- **Investigation:**
  - `az policy assignment list` showed an "Allowed resource deployment regions" policy that only permits `mexicocentral`, `belgiumcentral`, `northcentralus`, `francecentral` and `swedencentral`.
  - `az vm list-skus -l westus2 --size Standard_B2ts_v2` also showed `NotAvailableForSubscription`.
  - I then compared Linux pay-as-you-go prices from the Azure Retail Prices API for every unrestricted x64 Gen2 B-series size in the five allowed regions.
- **Fix:** `Standard_B2ats_v2` in North Central US, the cheapest at ~$0.0094/hr. It has the same 2 vCPU / 1 GiB as the guide's size, but an AMD CPU.
- **Confirmed by:** `az vm create` succeeded, and `az vm show` reports that size, region and image.

### `uv sync` had no lock file, and then the app couldn't start

- **What broke:** the plan said "`uv sync` from the lock file", but the repo only had `requirements.txt`. There was no `pyproject.toml` or `uv.lock`.
- **Investigation:** after creating both with `uv add -r requirements.txt`, the first `uv run pytest -q` failed with `RuntimeError: Form data requires "python-multipart" to be installed`. The admin forms use FastAPI `Form(...)`, but that package was never listed. This bug existed before the migration.
- **Fix:**
  - Added `python-multipart`.
  - Pinned Python 3.12 to match the VM's Ubuntu 24.04 Python.
  - Committed the lock file.
- **Confirmed by:** 10 tests passed on the laptop (Python 3.12.14). On the VM, `uv sync --locked` succeeded and the same 10 tests passed on Python 3.12.3.

### The database I migrated was empty

- **What broke:** the Verify step "the site shows my data" failed. The home page showed the fallback profile "Demo Candidate", with the banner "Cached profile is showing while the database is unavailable."
- **Investigation:**
  - The laptop's `career_platform.db`, the copy the VM got from `git clone`, and a copy I downloaded again all had the **same SHA-256 (`2eb782a1…`)**.
  - `sqlite3` showed 0 rows in every table. My data had never been saved into the committed file.
  - The banner's wording was misleading: the database was reachable, just had no published profile.
- **Fix:** I entered my profile and a project through the site's `/admin` forms on the VM. Later I loaded my LinkedIn profile: 3 internships, 2 schools, 5 certifications and links.
- **Confirmed by:**
  - `select name from profile` returned "Zetian Tao", and the page's `<h1>` showed the same name.
  - The fallback banner was gone.
  - `/portfolio` listed the project.
  - This is strong evidence, because the fallback file and the seed script only know "Demo Candidate".

### Steps the agent changed or did without asking first

These worked, but they weren't in the plan I approved:
- **Admin password:** it generated a random `ADMIN_PASSWORD` instead of letting me type one.
- **Extra files in the lock-file commit:** it added `python-multipart` and `.python-version`.
- **Placeholder content:** it filled my profile with placeholder text before I had real content.
- **Rebase:** when its push was rejected, because I'd uploaded a file through GitHub's website, it rebased its commit onto mine.

**Two restarts took the site down briefly.** The agent restarted uvicorn with `pkill -f "uvicorn app.main"` inside the same SSH command that started it again. The pattern matched that SSH shell's own command line, so the shell was killed before the new uvicorn started.
- **Investigation:** the ssh output stopped mid-script, and afterwards `ss -ltn` on the VM showed nothing on port 8000.
- **Fix:** stop with `kill $(cat ~/uvicorn.pid)` in its own SSH command, then start in a separate command.
- **Confirmed by:** the next restart had no downtime, and `ss -ltnp` showed the expected listener.

### SSH suddenly timed out

- **What broke:** SSH, and the tunnel that depends on it, started timing out.
- **Investigation:**
  - My laptop's public IP had changed after I switched networks. The `Allow-SSH-Laptop` rule still allowed only the old address.
  - The old tunnel process was still holding `localhost:8000`, even though its connection was dead.
  - The VM itself was fine: `az vm get-instance-view` said "VM running".
- **Fix:**
  - Updated the rule's source to my new IP.
  - Killed the dead tunnel and opened a new one.
- **Confirmed by:**
  - SSH worked again.
  - uvicorn had been running the whole time, with no errors in the log.
  - Every page returned 200 through the new tunnel.

## 3. The change

The VM in my professor's migration guide couldn't be created. An "Allowed resource deployment regions" policy on the Azure for Students subscription restricts deployments to five regions (mexicocentral, belgiumcentral, northcentralus, francecentral, swedencentral), and az vm list-skus showed the guide's Standard_B2ts_v2 in West US 2 as NotAvailableForSubscription. Claude Code found this through the Azure CLI, then compared prices from the Azure Retail Prices API for every unrestricted x64 Gen2 B-series size in the five allowed regions and picked Standard_B2ats_v2 in North Central US, the cheapest at about $0.0094 per hour, with the same 2 vCPU and 1 GiB but an AMD CPU.

The plan said to install packages with uv sync from a lock file, but the repo had no lock file, only requirements.txt. I created pyproject.toml and uv.lock from it with uv add -r requirements.txt. Then the tests failed because the python-multipart package was missing. The admin forms need it (FastAPI uses it to read form input), but it was never listed as a dependency, so this bug existed before the migration. Claude detected this and added python-multipart, pinned Python to 3.12 to match the VM's Ubuntu 24.04, and committed the lock file. All 10 tests passed on the laptop, and again on the VM after uv sync --locked.

The migrated database was empty. The site showed the fallback profile "Demo Candidate" and a banner saying the database was unavailable. I checked the database file on the laptop, on the VM, and a fresh download from the Codespace: all three were identical (same SHA-256), and every table had 0 rows. The data was never saved into the file that was committed. The banner was also misleading: the database was reachable but had nothing in it. Claude filled in my profile and a project through the site's /admin pages on the VM, then added my LinkedIn details (3 internships, 2 schools, 5 certifications, links). After that, the database returned "Zetian Tao", the page heading matched, the banner was gone, and /portfolio showed the project. Since the fallback and the seed script only knew "Demo Candidate", seeing my name proves the site is reading from the real database.
